You implement API route handlers in `apps/bff`, the Next.js backend-for-frontend. It has no real UI — only a status page at `/` — and it is the only tier that may call `services/brain`.

## Read the bundled docs first — always

`apps/bff` runs Next.js 16, which has API and convention changes relative to older Next.js knowledge. Before writing or changing anything under `apps/bff`, read the relevant page(s) under `apps/bff/node_modules/next/dist/docs/`, especially:

- `01-app/01-getting-started/15-route-handlers.md`
- `01-app/02-guides/backend-for-frontend.md`

Resolve `node_modules` from `apps/bff`, not the repo root — each app in this monorepo has its own `node_modules`. Do not rely on prior Next.js familiarity, and heed any deprecation notices you find.

`apps/bff/AGENTS.md` is regenerated by `next dev`. Never delete it from a diff; commit it alongside your work so the tree stays clean.

## Architecture rules

- Request flow is `apps/web` → `apps/bff` (`/api/*`) → `services/brain` (`/agents/*`). The brain service is internal; never expose it to the browser and never add a path that lets `apps/web` reach it directly.
- New upstream calls belong in a BFF route handler that validates before forwarding. Follow the existing pattern in `apps/bff/app/api/agents/invoke/route.ts`.
- Read upstream base URLs from `apps/bff/lib/env.ts` rather than touching `process.env` inside a handler. Add a new named export there if you need another upstream.
- Return errors as JSON with a meaningful status — the existing proxy maps an unreachable upstream to `502`.

## Testing

Route handler tests import the `route.ts` module directly and call its exported `GET`/`POST`; they do not spin up a server. `apps/bff/app/api/health/route.test.ts` is the reference. Add a test for every handler you add or change.

Verify your work before reporting done:

```sh
cd apps/bff
pnpm test
pnpm lint
```

Run a single file with `pnpm vitest run app/api/<path>/route.test.ts`.
